### [单卡从零训练 210M 文生图 DiT 的三项实测](https://www.reddit.com/r/MachineLearning/comments/1wdfmvq/training_a_210m_texttoimage_dit_from_scratch_on/) ⭐️ 8.0/10

一位实践者从零训练了一个 210M 参数的文生图扩散 Transformer（DiT），在单张 RTX PRO 6000 上耗时 3.5 天、使用 4.2M 张 256² 图像，并报告了三项具体测量结果。第一，遵循 register-token 思路，模型在图像流中设置 16 个 register token，并在每个交叉注意力中附加 2 个可学习 key/value 槽位；在中间块的中等噪声水平下，这 2 个槽位接收约 90% 的交叉注意力质量，而通常作为注意力汇的 EOS token 降至约 4%，register 向量在中间块增长到图像 token 范数的 4–13 倍。第二，流匹配损失是健康信号而非质量信号：整个训练中损失从 0.805 降至 0.754，而留出集 FID 从 33.7 降至 27.0、FD-DINOv2 从 570 降至 218、基于检测器的物体准确率从 65% 升至 90%，且训练与留出损失在 24 个 epoch 内保持到小数点后三位相等。第三，训练时的时间步偏移比将步数翻倍更有价值：在 2,456 条留出提示上，20 步配合偏移 2.8 得到 FID 27.0，50 步为 26.6，8 步为 28.4，20 步无偏移为 27.3 且 FD-DINOv2 从 218 升至 228；偏移 2.8 来自 SD3/RAE 针对 32 通道 FLUX.2 潜变量的规则 √\(32·32·32/4096\)。

reddit · r/MachineLearning · /u/IvanMikhnenkov · 9月11日 13:00

**「背景」** 扩散 Transformer（DiT）将 Transformer 架构用于扩散模型的去噪主干，近年来成为文生图生成的主流方案之一。交叉注意力中的“注意力汇”指模型倾向于将大量注意力质量集中到少数无内容语义的 token（如 EOS）上，register token 是视觉 Transformer 中用于吸收这类多余注意力的可学习占位符。流匹配（rectified flow）是一种训练扩散模型的目标，其损失衡量预测速度场与目标速度场之间的差异。

**「影响」** 该报告为在单张消费级或专业级 GPU 上从零训练中小规模文生图 DiT 的实践者提供了可复现的配置与量化参考，尤其是关于 register token 注意力汇行为、流匹配损失与生成质量脱钩、以及时间步偏移对少步采样质量影响的具体数据。

### [RTK 宣称节省 token，成本基准测试却提出质疑](https://quesma.com/blog/does-rtk-make-ai-coding-cheaper/) ⭐️ 7.0/10

Quesma 博客发布了一项成本基准分析，对 RTK 这一 AI 编码 token 节省工具宣称的收益提出质疑，认为其报告的 token 节省并未转化为实际成本下降。分析指出，RTK 的节省统计没有考虑下游命令的影响，例如代理运行 \`rtk command-that-prints-100k-tokens \| tail -5\` 时，实际只消耗约 100 个 token，但 RTK 仍会报告节省了 10 万 token。此外，RTK 默认持久化保存节省统计数据，会破坏沙箱隔离，并偶尔导致自动模式拒绝。社区评论中，gillesjacobs 引用文章数据称，Claude/Fable 的平均每次尝试成本仅从 1.72 美元降至 1.64 美元（约便宜 5%），DeepSeek 则从 0.115 美元升至 0.121 美元（约贵 5%），且 Claude 的节省几乎全部来自单个任务，剔除后节省不足 1%。

hackernews · michalwarda · 9月11日 11:15 · [社区讨论](https://news.ycombinator.com/item?id=49656471)

**「背景」** RTK（Rust Token Killer）是一款开源 CLI 代理工具，官方宣称可在常见开发命令上减少 60%–90% 的 LLM token 消耗，其做法是在命令输出进入 AI 上下文窗口之前先进行压缩，并以单个 Rust 二进制、零依赖的形式分发，通过全局 shell 钩子兼容 Aider、Gemini CLI、Codex、Windsurf 等终端 AI 工具。围绕这类“预处理省 token”工具的争议在于：其统计的节省量是否等于真实成本下降。已有第三方基准（如 JetBrains 博客对 Claude Code 的测试）指出，RTK 记录的节省数字可能被高估，例如一次读取 1.2 MB CSV 被记为节省 32 万 token，但 Claude Code 本身会提前截断过长的工具结果，实际差异远小于报告值。

**「影响」** 对使用 RTK 的 AI 编码团队而言，实测成本并未随其宣称的 token 节省而下降：Quesma 在花费超 1500 美元、历时数天的基准测试中发现，Claude/Fable 平均每次尝试成本仅从 1.72 美元降至 1.64 美元（约 5%），且几乎全部节省来自单一任务，剔除后不足 1%；DeepSeek 反而从 0.115 美元升至 0.121 美元（约贵 5%）。JetBrains 的独立试验也显示低努力下成本中位数上升 7.6%、高努力下持平，未出现节省。

**「社区讨论」** 评论者普遍质疑此类 token 节省工具，aeneas\_ory 称这些“hack”是 snakeoil，并分享用本地代码嵌入模型索引代码库可显著减少 token 使用和墙钟时间；oefrha 认为无需基准测试，仅看 rtk gain 输出就能发现 \`tail -5\` 等下游命令未被计入，且持久化统计会破坏沙箱；ProjectBarks 称 RTK 和 Headroom 的基准测试均未显示真实节省，并呼吁独立基准测试。也有评论者提到使用 treesitter 构建文件与目录大纲的替代方案。
